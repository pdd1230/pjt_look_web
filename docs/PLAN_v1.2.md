## 1. 진행 및 승인 규칙

4. 승인된 범위의 구현 오류는 해당 범위에서 수정한다. 새 기능, 판정 알고리즘의 큰 변경, DB 구조의 큰 변경은 변경 계획을 먼저 제출한다.

7. 비전 에이전트는 향후 별도 계획과 승인을 통해 재개한다.

## 2. P · Plan — 목표와 현재 상태

### 2.1 목표

기존 손가락 판정 로직을 재사용하여 교육용 웹서비스를 구축한다.

- 사진: 등록 → 수기 정답 작성·확정 → 추론 → 예측 저장 → 정답 비교 → 오답 분석.
- 실시간 웹캠: 브라우저 카메라 → 연속 프레임 전송 → 반복 추론 → 현재 개수 갱신.
- 동영상: 업로드 → 순차 프레임 분석 → 결과 영상·프레임별 예측 CSV → 선택 프레임 평가.

정답은 사람이 사진을 확인해 작성하고, 예측은 프로그램이 별도로 기록한다. 정답을 작성하지 않아도 추론은 가능하되 평가는 대기 상태로 둔다.

## 4. 기술 구성과 입력 처리

| 계층 | 제안 기술 | 적용 방향 |
|---|---|---|
| 화면 | HTML·Bootstrap·JavaScript | 학생이 이해하기 쉬운 단순 화면 |
| 서버 | FastAPI·Uvicorn·Jinja2 | 기존 Python 코드 재사용 |
| 추론 | MediaPipe·OpenCV·기존 판정 규칙 | 입력 종류와 무관하게 같은 핵심 판정 사용 |
| DB | MySQL·SQLAlchemy | 정답·예측·평가 연결 저장 |
| 파일 | 프로젝트 전용 저장 폴더 | 영상·이미지 보관, DB에 참조와 메타데이터 저장 |

사진·캡처 이미지의 바이너리 저장 여부는 크기를 기준으로 정하되, 이번 기본안은 정답 평가용 원본 이미지와 분석용 이미지를 파일로 보관하고 DB로 연결하는 방식이다. 영상 원본·결과 전체는 DB BLOB에 넣지 않는다. 입력·추론·결과의 연결과 파일 존재를 검증한다.

### 4.1 사진

- 실제 디코딩 가능 여부·형식·용량·픽셀 수를 확인한다.
- 촬영 방향 정보를 반영하고, 큰 이미지는 비율을 유지해 분석용으로 축소한다.
- 원본을 덮어쓰지 않고 원본·분석용·결과 이미지를 구분한다.
- 원본/분석 크기와 전처리 정보를 기록해 재현 가능하게 한다.

### 4.2 실시간 웹캠

- 서버 PC의 OpenCV 카메라가 아닌 사용자 브라우저의 카메라를 사용한다.
- 초기 분석 목표는 초당 3~5회다. 이는 실측 전 목표이며 화면 재생 FPS와 구분한다.
- 브라우저에서 프레임과 촬영 시각을 보내고 서버에서 결과를 반환한다.
- 세션마다 처리 대기열을 제한하고 오래된 대기 프레임 대신 최신 프레임을 분석한다.
- 손별 0~5개, 전체 0~10개, 손 미검출 상태와 실측 분석 속도를 표시한다.
- 모든 프레임을 영구 저장하지 않는다. 선택한 평가 캡처와 세션 요약을 저장한다.
- 단일 사용자 PC 기준으로 시작하며, 동영상 작업이 웹캠 처리를 장시간 막지 않도록 추론 실행을 조정한다.
- localhost에서 우선 검증한다. 다른 PC의 카메라 사용은 HTTPS 등 브라우저 조건을 확인해야 한다.

### 4.3 동영상

- MP4를 우선 검증하고 코덱·길이·크기 제한은 환경 확인 후 확정한다.
- 상태를 대기/분석 중/완료/실패로 표시하고 진행률을 제공한다.
- 기본 평가 모드는 읽을 수 있는 모든 프레임을 순서대로 분석한다.
- 성능상 프레임 간격을 두는 옵션을 추가한다면 처리 간격과 분석 프레임 수를 명시하고, 미분석 프레임을 추론 완료로 기록하지 않는다.
- 프레임 번호·원본 시각·손별/전체 개수·검출 상태를 CSV에 기록한다.
- 관절·개수가 표시된 결과 영상을 제공한다. 원본 음성 보존은 이번 필수 범위에 포함하지 않는다.
- 실시간보다 느릴 수 있으며, 실제 처리 시간과 처리 속도를 측정해 보고한다.

## 5. 사진별 수기 정답문서

사진 등록 시 빈 정답 양식을 만들고 사용자가 직접 작성한다. 모델의 예측값은 정답 입력란에 자동 복사하지 않는다.

| 항목 | 작성 방식 | 예시 |
|---|---|---|
| 입력 ID·파일명 | 자동 | IMG-001 / hand_001.jpg |
| 실제 손 개수 | 수기 | 1 |
| 실제 전체 손가락 개수 | 수기 | 3 |
| 손별 개수 | 수기 | 화면 왼쪽 2 / 오른쪽 3 |
| 조명 상태 | 사용자 선택·직접 입력 | 밝음, 어두움, 역광, 혼합 |
| 촬영 조건 | 사용자 선택·직접 입력 | 정면, 측면, 회전, 근거리 |
| 가림·배경 | 사용자 선택·직접 입력 | 엄지 가림, 복잡한 배경 |
| 비고 | 자유 수기 | 엄지와 검지가 겹침 |
| 작성자·시각 | 작성자 입력·시각 자동 | 담당자 / 작성 시각 |
| 상태 | 사용자 지정 | 미작성 / 작성 중 / 확정 / 판정 불가 |

- 정답 작성 화면에서는 예측값을 기본적으로 숨긴다.
- 손이 없으면 실제 손 개수 0, 손가락 개수는 빈 값이다. 주먹은 손 개수 1 이상, 손가락 개수 0이다.
- 손별 정답은 원본 방향을 기준으로 화면 왼쪽부터 식별하며 좌우 반전 여부를 명시한다.
- 확정 정답 수정 시 새 버전을 만들고, 평가가 참조한 정답 버전을 보존한다.
- 원인분류·비고는 사람이 작성·수정한다. 조명 조건만으로 오답 원인을 확정하지 않는다.

## 6. 예측결과 기록과 DB 구성

### 6.1 예측 기록

- 입력 ID, 분석 실행 ID, 세션 또는 영상 ID.
- 영상·웹캠 프레임 번호와 촬영/원본 시각.
- DETECTED / NO_HAND / ERROR 상태.
- 손별 개수·전체 합계·손가락별 펴짐 상태·랜드마크.
- 처리 시간, 모델 식별 정보, 알고리즘 버전, 전처리 정보.
- 결과 이미지/영상 위치와 분석 시각.

NO_HAND의 손가락 개수는 빈 값으로 저장한다. confidence 임계값을 손가락 수 정확도로 표시하지 않는다. 재분석은 새 실행으로 저장하고 기존 결과를 덮어쓰지 않는다.

### 6.2 논리 테이블 계획

| 테이블 | 역할 |
|---|---|
| inputs | 사진·영상·평가 캡처, 파일 참조·입력 정보 |
| ground_truths | 수기 정답, 조명·조건·비고, 확정 상태·버전 |
| analysis_runs | 입력별 분석 실행, 모델·알고리즘 버전·진행 상태 |
| vision_inferences | 사진 또는 영상 프레임의 예측·랜드마크·결과 참조 |
| evaluations | 정답 버전과 추론 연결, 일치 여부·오차·오류 유형·수기 원인 검토 |
| capture_sessions | 웹캠 세션과 캡처 연결·처리 요약 |

비전 에이전트용 agent_actions 테이블은 만들지 않는다. 영상 작업 상태는 analysis_runs에서 관리한다. FK 연결과 저장 실패 시 롤백을 검증하고, 파일 저장과 DB 기록이 엇갈린 경우 실패 표시·정리 방식을 마련한다.

## 7. 정답 비교와 오답분석표

첨부 파일의 실제 이름인 data/test_cases.csv를 기준으로 한다. 기존 열과 검출·분류·오류처리 구분을 유지한다.

| 기존 열 | 작성 규칙 |
|---|---|
| 테스트id | 자동 부여 |
| 시나리오_id | 입력과 테스트 조건 연결 |
| 기대동작 | 검출 / 분류 / 오류처리 |
| 입력파일명 | 입력에서 연결 |
| 예측(개) | 추론에서 자동 기록 |
| 정답(개) | 확정 수기 정답에서 연결 |
| 개수오차합 | 비교 가능한 값만 계산 |
| 성공여부(y/n) | 비교 규칙으로 판정 |
| 오류유형 | 미검출·오검출·과대계수·과소계수 등 초안 |
| 원인분류 | 사람이 확인·입력 |

추가 열: 입력 ID, 분석 실행 ID, 정답 버전, 프레임 번호·시각, 평가 상태, 조명, 촬영 조건, 비고, 검토 상태, 개선 의견.

### 비교 규칙

1. 검출 행에서는 실제·예측 손 개수를 비교한다. 이는 손 개수 일치 평가이며 박스 위치 정확도 평가는 아니다.
2. 분류 행에서는 전체 손가락 개수를 비교하고, 양손은 손별 정확도도 별도 집계한다.
3. 단일 손 오차는 절대값(예측−정답)이다. 손별 대응이 확실한 양손의 개수오차합은 손별 절대오차의 합이다.
4. 실제 손이 있는데 미검출이면 실패다. 예측 손가락 개수를 0으로 채우지 않고 숫자 오차는 빈 값으로 둔다.
5. 손이 없는데 검출되면 오검출이다. 손 없음과 주먹 0개를 분리한다.
6. 정답 미작성은 평가 대기, 판정 불가는 제외 사유를 기록한다. 성공여부는 빈 값으로 두어 실패와 구분한다.
7. 정답 수정·재분석 시 새 평가 기록을 만들고 기존 기록을 보존한다.
8. 전체 테스트표와 오답만 필터링한 표를 제공한다. CSV는 엑셀 한글 호환을 고려해 UTF-8 BOM으로 내보낸다.

### 집계

- 확정·평가 가능한 전체 사진을 분모로 손가락 전체 개수 일치율을 계산하고, 실제 손 미검출도 실패에 포함한다.
- 평가 대기·판정 불가 건수는 따로 표시한다.
- 손 개수 일치율, 전체 손가락 개수 일치율, 손별 일치율을 구분한다.
- 조명·각도·가림별 오답 건수와 해당 조건의 전체 평가 건수를 함께 표시한다.

## 8. 웹캠·동영상의 정답 평가

- 웹캠: 평가할 순간을 캡처하고 사진과 같은 정답 양식을 작성한다.
- 동영상: 선택한 원본 시각의 프레임을 추출하고 정답을 작성한다.
- 프레임 정답은 원본 영상 ID·시각·프레임 번호와 연결한다.
- 확정 정답이 있는 프레임만 정확도를 계산한다. 전체 영상 정확도인 것처럼 표현하지 않는다.
- 프레임별 전체 예측 CSV와 정답이 있는 프레임의 테스트표를 구분한다.

| 단계 | 주요 작업 | 확인 결과 |
|---|---|---|
| 1 | 환경·모델·기존 사진 추론 기준 확인 | 기존 로직의 기준 결과·환경 기록 |
| 2 | 공통 추론 서비스·상태 분리 | 세 입력에서 재사용할 결과 구조 |

| 4 | 사진 추론·결과 조회 | 정답과 예측의 분리 및 재분석 이력 |
| 5 | 비교·오답표·CSV | test_cases.csv 구조를 반영한 결과 |
| 6 | 실시간 웹캠 | 연속 추론·최신 프레임·세션 격리 |

| 8 | 통합 검증·설명서 | 실제 결과·미검증 항목·실행 절차 |

잠정 수업 일정은 **5주 × 주 7시간 = 35시간**으로 제안한다. 에이전트 보류로 확보되는 시간은 실시간 입력·영상 처리·평가 검증에 사용한다.

| 주차 | 7시간 내 주요 작업 |
|---|---|
| 1주 | 환경 확인, 공통 추론, 사진 업로드·기초 결과 |
| 2주 | MySQL, 수기 정답문서, 결과 저장·이력 |
| 3주 | 정답 비교·오답분석표, 실시간 웹캠 기본 연결 |
| 4주 | 웹캠 안정화, 동영상 분석·출력 |
| 5주 | 독립 평가, 예외·통합 검증, 수정·문서화 |

이는 교사 템플릿과 사전 환경 준비를 전제로 한 목표다. 1단계에서 장비·기존 코드 문제를 확인한 뒤 일정을 구체화한다. 필수 기능의 축소가 필요하면 임의로 제외하지 않고 변경 계획을 제출한다.

## 10. C · Check — 검증과 완료 기준

| 영역 | 검증 기준 |
|---|---|
| 사진 흐름 | 정상 사진 10건 연속 등록·추론·저장·조회 성공 |
| 정답 | 개수·조명·비고·확정·수정 버전 저장 확인 |

| 양손 | 전체 합계와 손별 결과 확인, 합계만 같고 손별로 틀린 사례 구분 |
| 웹캠 | 5분 연속 분석, 정지·재시작, 지연 누적·세션 상태 혼입 확인 |

정확도와 처리 속도는 사전 목표이며 달성치가 아니다. 기존 튜닝 데이터와 독립 평가 데이터를 분리한다. 학생 PC에서 확인해야 하는 카메라·코덱·MySQL 항목은 실제 확인 전까지 미검증으로 표시한다.
